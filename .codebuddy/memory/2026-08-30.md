# 2026-08-30

## email-scraper.ts：候选页识别改为双信号打分（路径 + 锚文本）

用户否决了 `if (matched) continue;`（路径命中即跳过锚文本匹配），要求路径命中后**继续**做锚文本匹配。

### 最终打分模型
两个信号各自独立打分，然后合并：
- `pathScore`：CANDIDATE_PATTERNS 按 URL 路径匹配（0 表示未命中）
- `anchorScore`：ANCHOR_PATTERNS 按链接文字匹配（0 表示未命中）
- `finalScore = max(pathScore, anchorScore) + (bothMatched ? BOTH_MATCH_BONUS : 0)`，`BOTH_MATCH_BONUS = 10`
- `finalType` 取信号更强的一方；两者都为 0 则跳过该 href

设计理由：路径与文字双命中 = 互相印证、可信度更高，排序时优先抓取。实测排序：
```
/contact      路径100 文字88  双命中 → 110
/contact.html 路径100 文字88  双命中 → 110
/support      路径88  文字70  双命中 → 98
/company      路径0   文字88  仅文字 → 88   ← 路径看不出名但能靠文字捞回
/team         路径30  文字45  双命中 → 55
/blog         文字超长 → 排除   /random 双不命中 → 排除
```

### 性能改造（重要）
原 `extractAnchorText(html, href)` 对每个 href 都对整个 HTML 跑一次 new RegExp（O(n×m)）。改成路径命中也匹配后，所有 href 都要查锚文本，性能会明显恶化。
→ 新增 `buildAnchorTextMap(html)`：**一次扫描**建立 `href → 链接文字` 的 Map（去标签/去 &nbsp;&amp;/压缩空白/长度 >40 丢弃），循环内直接 `map.get(href)` 查表。已删除 extractAnchorText。

### 用户偏好补充
- 用户不认可"命中即停止/跳过"的短路写法，倾向于让多个信号都参与、合并打分，而非互斥分支。
- 剩余 7 个 pre-existing lint 错误（verifyEmail DNS 死代码段：biome noUnreachable + TS18046 dataA/dataMX unknown）仍在，用户暂未要求清理。

### 追加：BOTH_MATCH_BONUS 已删除（用户第二次质疑后撤销）
用户质疑"双命中加分有必要么？总不是都要抓取的"——质疑成立：scrapeLevel2and3 全抓候选页，排序只在 (a) 候选页 >20 截断、(b) 串行抓取顺序容错 两个边缘场景有意义。已删除 `BOTH_MATCH_BONUS = 10`，`finalScore = Math.max(pathScore, anchorScore)`，finalType 仍取信号较强一方（仅用于日志）。双命中现在只是"两个信号都指向同一页"的自然结果，不再额外加权。

### 追加：HTTP 缓存讨论 → 最终改为 fetch cache:"reload"（两轮迭代）
用户观察到同一 URL 一次 200（浏览器导航，完整内容有邮箱）一次 304（扩展 background fetch，内容是"部分的"、无邮箱），提出三方案：①加 no-cache 请求头 ②直接用 fetchWithBrowserTab ③fetch 没匹配到邮箱再升级浏览器。
**第一轮采纳①**（HEADERS 加 Cache-Control: no-cache），但用户随后指出 304 回填内容不完整——**①治不了**：no-cache 的动作就是 revalidate，服务器确认没变照样 304 回填那份有问题的副本。
**第二轮改为 fetch option `cache: "reload"`**（删掉请求头）：不发条件请求、不读缓存、强制全量 200，内容完整性优先于流量（批量抓取是一次性读取，不依赖缓存加速）。MV3 SW 环境支持（仅 only-if-cached 有 mode 限制）。
**用户实测 reload 后依旧 304 + 0 邮箱**（未验证扩展是否重载/看的是否 SW 的 DevTools；若 reload 生效请求不应带 If-None-Match 也就不该 304）。
**根因判定（大概率）**：studioeditor.io 是 Vercel 托管的 Next.js 站，邮箱在 hydration 后才插入 DOM，fetch 拿到的静态 HTML 里从来就没有——200/304 与缓存都只是表象，"没执行 JS"才是根因（同 launchigniter 老坑）。验证法：浏览器 Ctrl+U 查看源代码搜邮箱，搜不到即实锤。
**第三轮：已上受限版③**——scrapeLevel1 中首页 fetch 提取 0 邮箱时，调 fetchWithBrowserTab 完整渲染兜底一次（仅首页、每站最多一次）；渲染版有邮箱则同时用渲染版 HTML 找候选页（DOM 导航链接更全）。0 邮箱站（本来无公开邮箱）会多花一次 tab 成本，用户产出导向下接受。注意 biome useConst：兜底分支用 renderedEmails 新变量 return，外层 emails 保持 const。

### 追加：用户指出 response.ok 拦截漏洞 → 删除状态码拦截 + fromBrowser 防重复
用户发现 `if (!response.ok) return ""` 会短路浏览器兜底：304 透传时 response.ok=false（ok 仅 200-299）、text() 为空 → scrapeLevel1 收到 "" → 直接 return，fetchWithBrowserTab 永远不执行。403/429 反爬同理被拦截——而真实浏览器恰是最可能过反爬的路径。
**修复**：删除 attemptFetch 中 `if (!response.ok) return ""`，body（可能为空）直接交给 isSkeleton 判断（空必命中 length<10000）→ 自动升级 tab 渲染。一处删除同时覆盖 304 / 反爬 / SPA 空壳三类场景。
**防重复设计**：attemptFetch/isSkeleton 已 tab 兜底过、渲染后仍 0 邮箱（站真没邮箱）时，scrapeLevel1 的 0 邮箱兜底会再开一次 tab（浪费 3-15s）。为此引入 `FetchResult { html, fromBrowser }`：attemptFetch 返回 fromBrowser 标记，scrapeLevel1 兜底条件为 `emails.length === 0 && !fromBrowser`。fetchWithTimeout 签名改为 Promise<FetchResult>，网络错误重试耗尽返回 { html:"", fromBrowser:false }（连不上时 tab 也没用，不兜底）。scrapeLevel2and3 候选页解构 `const { html: candidateHtml }`。attemptFetch 签名同步改 FetchResult（接口定义前置于 attemptFetch 之上，否则 TS2322）。

### 追加：删除状态码拦截引出的两个漏洞自查修复
1. **404/410 触发无效 tab 渲染（性能回归，必修）**：去掉 response.ok 后，失效的候选链接（模板里 /team、/careers 实际不存在，很常见）返回 404 短页面 → isSkeleton 命中 → 白等一次 tab（每站可能 3×15s）。已加：`status === 404 || 410` 直接返回 { html:"", fromBrowser:false }（浏览器也拿不到不存在的内容）。注意此时 html 为空，scrapeLevel1 的 `!html` 会提前 return，不会误开 tab。
2. **tab 渲染失败后重复开 tab**：isSkeleton 已开过 tab 但超时返回空时 fromBrowser 仍是 false → scrapeLevel1 再开一次。已改为 tab 失败也返回 `fromBrowser: true`，且保留原骨架 html（SPA 骨架里可能仍有导航链接可用于找候选页）。
3. 未改的 pre-existing 项（已向用户报告）：isSkeleton 的 10000 字符阈值会把"短但正常的静态页"误判为骨架并开 tab；fetchWithTimeout 最坏 5 次 ×30s = 150s；浏览器 tab 用自身缓存不受 cache:"reload" 影响。

### 追加：字段重命名 fromBrowser → browserTried + isSkeleton 阈值下调
用户对"漏洞2"提出质疑："不是有判断 fromBrowser 么"——判断确实存在，但**值设错了**：`if (browserHtml) return {...fromBrowser:true}` 只在 tab 成功时置 true；tab 失败（返回空）会掉到末尾 `return { html, fromBrowser:false }`，"已尝试过"的事实丢失 → 上层 `!fromBrowser` 成立 → 再开一次 tab。
**修复 + 改名**：字段语义实为"已尝试过浏览器兜底（无论成败）"，故重命名 `fromBrowser` → `browserTried`，tab 失败路径也置 true。涉及 FetchResult 接口、attemptFetch 三处 return、fetchWithTimeout 三处 return、scrapeLevel1 两处。踩坑：replace_all 只覆盖了 `return { html: "", fromBrowser: false };`（2处，带缩进），fetchWithTimeout 末尾 `return { html: "", fromBrowser: false };`（另2处，无前导空格）需单独改，否则 TS2353。
**isSkeleton 阈值 10000 → 2000**（提为常量 SKELETON_MIN_LENGTH）：以 SPA 空壳特征（div#root/div#app 为空）为主，长度仅兜空响应/错误页，避免误伤 3-5KB 的精简静态页（如手写 contact.html）。空字符串仍命中（length 0 < 2000），304 空 body 的兜底链不受影响。
**仍未处理（已告知用户，待决策）**：fetchWithTimeout 最坏 5×30s=150s（建议候选页用短超时少重试）；浏览器 tab 用自身缓存不受 cache:"reload" 影响。
